Providers & Models — 5 topics

  1. How a chat model is derived

    Every hosted assistant comes off the same line: pretrain a transformer on a huge corpus to get a base model that only continues text, instruction-tune it so it follows requests, then align it with human or AI feedback so it is helpful and refuses sensibly. The thing you call over an API is the end of that chain, never the base model.

  2. Providers & their families

    Six names cover almost everything in production. What separates them for an engineer is not benchmark position — which changes monthly — but whether the weights are downloadable, what the context window is, and what a million tokens costs.

  3. Open vs closed weights

    Closed models are an API — you get capability and no control. Open weights you can download, fine-tune, quantize and run on your own hardware, which is what makes privacy, offline use and per-token-free inference possible at all. The trade is that you now own the serving, the GPUs and the quality gap.

  4. Choosing a tier

    Within a family the tiers exist so you do not pay frontier prices for simple work. The practical rule: start on the most capable model to prove the task is possible at all, then step down tier by tier while an eval set tells you quality still holds. Most production traffic ends up on a mid tier.

  5. Staying provider-agnostic

    Model names change, prices change, and a provider you depend on will have an outage. Keeping one interface in front of them — a router with a fallback order — means a model change is configuration rather than a refactor, and an outage is a slower answer instead of an error page.
