Systems I've Built — 3 systems

The strongest material in an interview, because the trade-offs are ones I actually hit.

  1. Web crawler

    Collect pages continuously from sites that don't want to be crawled fast. The design centres on a URL frontier with priority and politeness queues, per-domain rate limits, dedup of both URLs and near-identical content, and checkpointing so a crash doesn't lose a whole run.

    Resources
    Learn
    • System Design Primer — design a web crawler
    • Scrapy architecture overview — a real frontier and scheduler, documented
    • Hello Interview — the crawl-scale estimation pattern
    Practice
    • Web Crawler Multithreaded
    • Web Crawler
    My code

    The Q-Commerce crawler isn't public. Worth pushing a trimmed version — it's your strongest case study.

  2. E-commerce / multi-vendor marketplace

    Many sellers, real money, and files that must not leak. Catalogue and inventory, reserving stock at checkout so two buyers can't take the last item, an order state machine, split payments to vendors, and webhook handling that survives duplicate delivery.

    Resources
    Learn
    • Stripe Connect docs — how split payments actually work
    • Stripe — webhook best practices — signature verification and replay safety
    • Saga pattern — the order/payment/stock rollback problem
    Practice
    • Design Movie Rental System — inventory across vendors
    • Design a Food Rating System
    My code
    • Digital-market-place-app — vendors, buyers, Stripe Connect, S3 downloads
    • Cart-session-cookie-Django — the cart/session layer

  3. RAG / LLM serving platform

    Grounded answers over a private corpus, at acceptable cost and latency. Chunking and embedding on ingest, ANN retrieval with re-ranking at query time, streaming responses, multi-provider fallback for reliability, and evaluation so quality changes are measurable.

    Resources
    Learn
    • pgvector — indexes, distance operators, tuning
    • LiteLLM docs — routing, fallbacks, cost tracking
    • Claude — tool use & agents — the agentic loop, documented
    Practice

    No LeetCode equivalent — the practice is building evals for retrieval hit-rate and groundedness.

    My code
    • lenny-growth-assistant — the full system, cloud or local via one env var
    • agents-from-scratch — the agent loop built up from first principles

Core Interview Systems — 7 systems

The ones that come up most. Worth being able to design cold.

  1. Rate limiter

    Deceptively deep for how small it looks. Where it sits (gateway, service or client), which algorithm, what key to count against (user, IP, endpoint), what to return on rejection, and how to keep a shared counter correct under concurrency across many instances.

    Resources
    Learn
    • Stripe — Scaling your API with rate limiters
    • Cloudflare — sliding window counters
    • Redis — rate limiting patterns
    Practice
    • Logger Rate Limiter
    • Design Hit Counter
    My code
    • Rate-limiter — fixed window; add sliding window and token bucket next

  2. URL shortener

    A tiny data model with a huge read:write ratio, so the whole design is about the read path. Key generation (counter + base62 vs hash with collision check), caching, 301 vs 302 — 302 if you want click analytics — plus custom aliases and expiry.

    Resources
    Learn

    • Gaurav Sen (YouTube) — the classic video walk-through
    Practice

    My code
    • URL-Shortner — base62 short-link generation

  3. News feed

    The fan-out question. Precomputing each user's feed on write gives fast reads but explodes for accounts with millions of followers; computing on read is cheap to write but slow. The real answer is hybrid — and raising the celebrity problem yourself is the signal.

    Resources

  4. Chat / messaging system

    Real-time delivery over persistent connections. A registry mapping user to the server holding their socket, message ordering by sequence number rather than timestamp, delivery and read receipts, presence, and push notifications for anyone offline.

  5. Notification system

    One dispatch API over push, email and SMS. A queue per channel, provider failover when one goes down, deduplication so a retry doesn't double-send, user preferences and quiet hours, template rendering, and tracking delivery state per recipient.

  6. Search autocomplete / typeahead

    A ~100 ms latency budget, so everything must be in memory and precomputed. A trie with the top-k completions cached at each node, rebuilt offline from query logs rather than updated on the write path, and sharded by prefix once it outgrows one machine.

Larger Systems — 8 systems

Bigger surface area — each one leans on a specific building block from HLD.

  1. Ticket booking system

    A pure concurrency problem wearing a product costume. Seats must be held while a user pays, holds must expire automatically, and no two people can ever get the same seat — under a traffic spike where everyone arrives in the same second.

    Resources

    • Hello Interview — Ticketmaster breakdown
    • PostgreSQL — explicit locking — SELECT … FOR UPDATE
    • Redis — distributed locks
    Practice

  2. Payment system

    Correctness matters more than latency. Idempotency keys on every charge, a double-entry ledger where money is never stored as a float, sagas with compensating actions across services, reconciliation jobs against the provider, and signed webhooks.

    Resources
    Learn
    • Stripe — idempotent requests
    • Fowler — accounting patterns — double-entry, properly explained
    • Brandur — idempotency keys
    Practice

    No LeetCode equivalent — implement a double-entry ledger where every transaction balances to zero.

    My code

  3. File storage & sync (Dropbox)

    Chunk files, address chunks by content hash, and you get deduplication and delta sync for free — only changed chunks travel. Metadata lives in a database, blocks in object storage, and conflict resolution handles two devices editing offline.
