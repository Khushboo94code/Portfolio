Foundations — 5 topics

  1. Concurrency vs parallelism

    Concurrency is structuring work so tasks can make progress independently; parallelism is literally running them at the same instant on different cores. A single-core machine can be concurrent but never parallel — and asyncio is concurrency with no parallelism at all.

  2. Processes vs threads

    A process owns its own memory; threads share the memory of their process. That single difference produces everything else — threads are cheap to start and dangerous to share state between, processes are expensive to start and safe by isolation.

  3. The GIL

    CPython holds one lock over the interpreter, so exactly one thread executes Python bytecode at a time. The lock is released during I/O waits, which is why threads help network and disk work and do nothing for pure computation. This is the question interviews ask.

  4. CPU-bound vs I/O-bound

    The only classification that matters when choosing a model. I/O-bound work spends its time waiting on something external, so overlapping the waits is free speed. CPU-bound work is limited by the processor, so only more cores help.

  5. When concurrency is the wrong answer

    Concurrency adds real cost: race conditions, harder debugging, nondeterministic tests. Often a better algorithm, an index, a cache or a batched query beats parallelising a slow thing. Measure first — Amdahl’s law caps your speedup at whatever fraction is actually parallelisable.
