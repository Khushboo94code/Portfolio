Beyond Relational — 4 topics

  1. NoSQL families

    Four shapes: key-value (Redis), document (MongoDB), wide-column (Cassandra) and graph (Neo4j). Each drops something relational databases guarantee in exchange for scale or flexibility, and each requires you to model around known access patterns.

  2. Choosing a database

    The honest default is Postgres until you have a specific reason to leave — it does JSON, full-text search, geospatial and vectors. "We need NoSQL for scale" is usually a schema or indexing problem wearing a costume.

  3. OLTP vs OLAP

    Transactional systems serve many small reads and writes; analytical systems scan huge ranges to aggregate. They want opposite things — row storage versus columnar, normalised versus star schema — which is why you do not run reporting queries against your production database.

  4. Extensions & vector search

    Postgres extensions let one database do more: pgvector for embeddings and semantic search, PostGIS for geospatial, full-text search built in. Keeping vectors beside relational data is why Lenny needs no separate vector store.
