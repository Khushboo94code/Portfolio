Transactions & Concurrency — 4 topics

  1. ACID

    Atomicity — all or nothing. Consistency — constraints hold before and after. Isolation — concurrent transactions do not see each other’s partial work. Durability — committed means survived a power cut. Four words you will be asked to expand and justify.

    PropertyMeaningExample
    A — AtomicityAll operations succeed, or all are rolled backMoney transfer
    C — ConsistencyDatabase stays valid before and after the transactionBalance cannot become invalid
    I — IsolationConcurrent transactions don’t interfere incorrectlyTwo users booking the same seat
    D — DurabilityOnce committed, data is permanently savedPayment survives a server restart

    Worked example — transferring ₹1,000 from A to B

    Two operations make up one transfer:

    1. Deduct ₹1,000 from A
    2. Add ₹1,000 to B
    1. Atomicity — all or nothing

    Either both operations happen, or neither does.

    A: ₹5000 → ₹4000
B: ₹2000 → ₹3000

    If adding to B fails, the deduction from A must roll back too:

    A: ₹5000   (unchanged)
B: ₹2000   (unchanged)

    This is exactly what transaction.atomic() gives you in Django:

    from django.db import transaction

with transaction.atomic():
    task1()
    task2()

    If task2() raises, task1() is rolled back with it.

    2. Consistency — the rules still hold

    Constraints must be satisfied before and after. Say the rule is balance cannot go negative, and A has only ₹500:

    Before: A = ₹500
After:  A = -₹500   ✗ invalid

    The transaction must fail rather than leave the database in that state — which is why this belongs in a CheckConstraint, not only in application code.

    3. Isolation — concurrent transactions don’t corrupt each other

    Two users try to book the last seat at the same moment:

    User A → checks seat → Available
User B → checks seat → Available   ✗ both now book it

    With the right isolation level or an explicit row lock (SELECT … FOR UPDATE), only one booking succeeds.

    4. Durability — committed means committed

    After COMMIT, the data survives anything:

    Transaction
    ↓
COMMIT
    ↓
Data permanently stored
    ↓
Server crashes
    ↓
Server restarts
    ↓
Data is still there   ✓

    Easy way to remember

    • A — All or Nothing
    • C — Correct / valid state
    • I — Transactions don’t interfere incorrectly
    • D — Data stays after commit

  2. Isolation levels & anomalies

  3. Locking & MVCC

    Postgres uses multi-version concurrency control, so readers never block writers and writers never block readers — a very different model from lock-everything databases. Explicit SELECT ... FOR UPDATE is how you serialise a row when you actually need to.

  4. Deadlocks in the database

    Two transactions each holding what the other needs. Postgres detects the cycle and kills one with SQLSTATE 40P01 — so your application must be ready to retry. Consistent ordering of updates is the prevention.
