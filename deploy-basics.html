Fundamentals — 5 topics

  1. What deployment actually is

    Running your code on a machine that is not yours, continuously, for people who are not you. Three things change versus runserver: it must survive restarts, it must not expose debug information, and configuration comes from the environment rather than from a file you edited by hand.

  2. Where code can run

    Four options, increasing in control and effort: a PaaS (Render, Railway, Fly) that takes your repo and handles the rest; a container platform; a plain VPS you administer yourself; and serverless. As a beginner, deploy to a PaaS first to get something live, then do it on a VPS to learn what the PaaS was doing.

  3. Domains & DNS

    Buying a name and pointing it at your server: an A record for an IP, a CNAME for another name. Changes are not instant because resolvers cache by TTL — lower the TTL before a migration, not during it.

  4. Environments — dev, staging, prod

    The same code with different configuration and different data. Staging exists so the risky first run of a migration or a deploy happens where nobody is watching. The rule that matters: never point staging at the production database.

  5. Secrets & configuration

    Anything that differs between environments is configuration; anything that would hurt if public is a secret. Secrets belong in the platform’s secret store or a vault — not in settings.py, not in the image, and not in a .env file that gets committed by accident.
