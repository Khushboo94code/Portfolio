  1. A server & SSH

  2. Gunicorn — the application server

    The dev server is single-process and explicitly not for production. Gunicorn runs multiple worker processes and speaks WSGI to Django. Worker count is the first tuning knob you will meet — start around 2×CPU+1 and measure.

    Resources
    Learn
    • Django — deploying with Gunicorn

    Practice
    • Run your app under Gunicorn locally and compare behaviour with runserver.

  3. Nginx — the reverse proxy

    Sits in front of Gunicorn: terminates TLS, serves static files directly, buffers slow clients so they do not tie up a worker, and routes. Almost every "502 Bad Gateway" is Nginx telling you Gunicorn died or never started.

    Resources
    Learn

    • Error codes reference — 502 vs 503 vs 504
    Practice

  4. Static & media files

    Django does not serve static files in production. collectstatic gathers them for Nginx or a CDN; user uploads (media) belong in object storage like S3, not on the server disk — otherwise they vanish the moment you redeploy to a fresh container.

    Resources

    Practice

  5. HTTPS with Let’s Encrypt

    Free, automated certificates via certbot, renewed on a timer. HTTPS is not optional — without it credentials travel in clear text. Then redirect HTTP to HTTPS and turn on HSTS so browsers refuse to downgrade.

  6. Keeping it running — systemd

    A process you started over SSH dies when you log out. A systemd unit starts Gunicorn on boot, restarts it on crash, and sends its output to the journal — which is also where you will read the logs when something breaks.

    Resources

    • Gunicorn documentation — see the deployment section

    Practice
