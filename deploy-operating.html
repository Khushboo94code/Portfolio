Operating It — 5 topics

  1. Logs you can actually use

    Log to stdout in structured form and let the platform collect it. Include a request ID so one user’s journey can be followed across services, and never log credentials or tokens.

    • Twelve-Factor — logs as event streams

  2. Monitoring & alerting

    Track what users feel — error rate, p95 latency, availability — not CPU. Alert on symptoms, and only on things a human should wake up for; an alert nobody acts on trains everyone to ignore alerts.

    Resources
    Learn
    • Google SRE — monitoring
    • Google SRE — implementing SLOs
    • Prometheus — overview
    Practice
    • Define one SLO for your app and an alert that fires only when it is genuinely at risk.

  3. Error tracking

    Logs tell you something happened; an error tracker groups the same exception, counts it, and gives you the stack trace with request context. It is the single highest-value thing to add after your first deploy.

  4. Scaling up and out

    Up means a bigger machine and is the easy first answer. Out means more instances and requires that your app holds no local state. Measure before either — most "we need to scale" turns out to be one missing database index.

    Resources
    Learn
    • Your HLD track — scaling, caching and statelessness
    • Django — performance and optimization
    • Twelve-Factor — stateless processes
    Practice
    • Load-test one endpoint, find the first bottleneck, and fix that rather than adding a server.

  5. Rollback & incidents

    Know how to get back to the last good version before you need to, and practise it. During an incident: restore service first, investigate afterwards. A short blameless write-up afterwards is what stops the same outage twice.

    Resources
    Learn
    • Google SRE — postmortem culture
    • Google SRE — emergency response
    • Fowler — blue-green — rollback as a switch
    Practice
    • Roll back a deploy deliberately and time it. If it takes more than a few minutes, fix that.
