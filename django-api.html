APIs with DRF — 6 topics

  1. Serializers & validation

    The boundary between JSON and your models — and the right place for input validation. ModelSerializer for the common case, nested and writable serializers for the hard ones, and validate_<field> / validate for rules that span fields.

  2. Views, ViewSets & routers

    The ladder from APIView to generic views to ModelViewSet — each step trading explicitness for less code. Routers generate URL patterns from a ViewSet, which is convenient right up until you need a non-CRUD endpoint and reach for @action.

  3. Authentication

    Session auth for browsers, token or JWT for clients that aren't. The trade-off worth being able to argue: JWTs scale statelessly but can't be revoked before expiry, which is why short access tokens plus refresh rotation is the usual compromise.

  4. Permissions & throttling

    Authorisation enforced server-side — object-level permissions so a vendor can only touch their own products, not just a UI that hides the button. DRF throttling is rate limiting applied at the framework layer, the same token-bucket idea from HLD.

  5. Pagination, filtering & versioning

    The difference between an API that survives growth and one that doesn't. Offset pagination degrades on large tables — cursor pagination doesn't. Filtering belongs in a declarative layer, and versioning is what lets you change a response shape without breaking clients.

    APIClient for request-level tests, factories instead of fixtures, and tests that don't hit the network. The design pressure matters as much as the coverage — code that's hard to test is usually code with the wrong seams.
