  5. View decorators

    The same decorator you write by hand, applied to a view. @login_required replaces the view with a wrapper that checks request.user first and only calls your code if the check passes — which is why the auth logic lives in one place instead of as an if at the top of every view.

    What the @ actually does

    from django.contrib.auth.decorators import login_required

@login_required
def create_task(request):
    return HttpResponse("Create Task")

is exactly

create_task = login_required(create_task)

    The name in your URLconf now points at the wrapper. Django calls that; the wrapper decides whether your function runs at all.

    Roughly what it contains
    def login_required(func):
    def wrapper(request, *args, **kwargs):
        if request.user.is_authenticated:
            return func(request, *args, **kwargs)
        return redirect(f"/login/?next={request.path}")
    return wrapper

    The real one is more capable — it takes login_url and redirect_field_name, so it is a decorator factory (one more nesting level), and it redirects rather than returning a string. The shape is the same.

    On a real view
    from django.contrib.auth.decorators import login_required
from django.http import HttpResponse

@login_required
def create(request):
    if request.method == "POST":
        # create task
        return HttpResponse("Task created")
    return HttpResponse("Send POST request")

    Note the wrapper must return what the view returns — a decorator that forgets this turns every view into None and Django raises “view didn't return an HttpResponse object”. That is bug 2 from Practise → snippet 21, seen in production.

    The ones worth knowing
    @login_required                     must be signed in
@permission_required("app.add_task") must hold a permission
@require_POST / @require_http_methods  wrong verb → 405
@csrf_exempt                        switches off CSRF — justify every use
@cache_page(60 * 15)                cache the whole response
@transaction.atomic                 roll back the view's writes on error
    On class-based views
    @method_decorator(login_required, name="dispatch")
class TaskCreateView(View): ...

or, more usual for auth:
class TaskCreateView(LoginRequiredMixin, View): ...

    A plain decorator expects a function, so a CBV needs method_decorator — or the mixin, which is the same idea expressed through the MRO.

    Decorator or middleware?
    decorator    one view, or a handful     opt in, visible at the view
middleware   every request              opt out, invisible at the view

    Auth on three views is a decorator. Request logging is middleware. Choosing the wrong one gives you either copy-paste or a global rule nobody can see from the code they are reading.
