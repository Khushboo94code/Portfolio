ORM Depth — 5 topics

Where Django meets the database chapters of HLD. This is the group that separates people who use the ORM from people who know what SQL it emits.

  1. QuerySets & lazy evaluation

    QuerySets don't hit the database until they're iterated, sliced or cast — which is why a filter chain costs nothing and an accidental len() inside a loop costs everything. Knowing exactly when evaluation happens is the whole topic.

    Practice

    My code

  2. N+1 queries & optimisation

    The single most common Django performance bug: one query for a list, then one more per row. select_related solves it with a join for forward FKs; prefetch_related with a second query for reverse and M2M. only, defer and values trim what you fetch.

    Resources
    Learn

    • select_related vs prefetch_related
    • nplusone — detects N+1 automatically in tests
    Practice
    • Find an N+1 in one of your own repos with the debug toolbar and fix it; record the query count drop.
    • Employees Earning More Than Their Managers — the self-join an ORM query hides
    My code
    • Django-Query-Params — the natural place to add optimisation examples

  3. Transactions, locking & race conditions

    atomic() blocks, why ATOMIC_REQUESTS is a blunt instrument, and select_for_update() for the "two users buy the last item" problem. transaction.on_commit is the fix for the classic bug of firing a Celery task before the row it needs is committed.

    Resources
    Learn
    • Django — database transactions
    • select_for_update reference
    • DBMS → Transactions & Concurrency — ACID, isolation levels and MVCC, worked through
    Practice
    • Reproduce a double-purchase with two concurrent requests, then fix it with a row lock.
    • Find any delay() called inside atomic() in your code and move it to on_commit.
    My code
    • Digital-market-place-app — checkout and payment, where this actually bites

  4. Indexes & database constraints

    Pushing correctness and speed down into the database: Meta.indexes for read patterns, UniqueConstraint and CheckConstraint so invalid rows can't exist even if application code has a bug. A constraint is a guarantee; a validator is a request.

    • Replace a unique_together with a conditional UniqueConstraint.

  5. Aggregation, annotation & raw SQL

    Computing in the database rather than in Python: annotate for per-row values, aggregate for totals, Subquery and Window for the harder shapes — and knowing when to stop and write raw SQL instead of a nine-line ORM expression nobody can read.
