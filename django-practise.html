  1. 01 — classmethod

    A method bound to the class rather than an instance. It receives cls instead of self, so you can call it without creating an object.

    class MyClass:
    @classmethod
    def displayinfo(cls):
        print("This is MyClass.")

MyClass.displayinfo()

    Output

    This is MyClass.
    Notes
    What to notice
    • No MyClass() anywhere — it is called straight on the class.
    • cls is the class itself, the way self is the instance.
    • It still works if you call it on an instance: MyClass().displayinfo().
    • cls follows the subclass — this is the whole point: 
      class Child(MyClass): pass

MyClass.displayinfo()   # cls is MyClass
Child.displayinfo()     # cls is Child
      which is why classmethods are used for alternative constructors — Model.objects.create(), datetime.fromtimestamp().
    classmethod vs staticmethod vs instance method
    • def m(self) — needs an instance, can read instance state
    • @classmethod def m(cls) — needs the class, can create instances of it
    • @staticmethod def m() — neither; just a function living in the class namespace
    Where you have seen it

    • Interview → What are decorators? — @classmethod is one

  2. 02 — __init__ and instance attributes

    The constructor. It runs when you create an object, and self.name = name is what makes the value stick to that instance.

    class Parent:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print(f"Hello from Parent class. My name is {self.name}.")

p = Parent("Alice")
p.greet()

    Output

    Hello from Parent class. My name is Alice.
    Notes
    What to notice
    • Parent("Alice") calls __init__ automatically — you never call it yourself.
    • self is passed automatically too. p.greet() is really Parent.greet(p).
    • self.name is an instance attribute — each object gets its own. A variable defined directly in the class body would be shared by all of them.
    • __init__ is not really a constructor — __new__ creates the object, __init__ initialises it. Worth knowing if asked.
    The trap worth remembering
    • A mutable default in a signature is created once, at definition time, and shared: 
      def __init__(self, items=[]):   ✗ shared between every instance
def __init__(self, items=None):  ✓
    self.items = items or []
    Next step
    • Add a Child(Parent) and call super().__init__(name) — that is inheritance, and the natural follow-up to this snippet.

  3. 03 — inheritance and super()

    Child extends Parent, adds its own attribute, and calls super().__init__() so the parent’s setup still runs. greet() is never redefined — it is inherited.

    class Parent:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print(f"Hello from Parent class. My name is {self.name}.")


class Child(Parent):
    def __init__(self, name, age):
        super().__init__(name)      # run Parent's __init__ first
        self.age = age


child1 = Child("Khushboo", 10)
child1.greet()

    Output

    Hello from Parent class. My name is Khushboo.
    Notes
    What to notice
    • Child defines no greet(). Python does not find it on Child, looks at Parent, finds it there, and uses it. That is inheritance doing its job.
    • super().__init__(name) runs the parent constructor, which is what sets self.name. Without it, greet() would have nothing to print.
    • Both attributes land on the same object: 
      child1.__dict__  →  {'name': 'Khushboo', 'age': 10}
    • The object is both types at once: 
      isinstance(child1, Child)   → True
isinstance(child1, Parent)  → True
    What happens if you forget super()

    This is the bug worth seeing once, so you recognise it instantly:

    class Broken(Parent):
    def __init__(self, name, age):
        self.age = age          # forgot super().__init__(name)

b = Broken("X", 5)
b.__dict__   →  {'age': 5}      ← no 'name'
b.greet()    →  AttributeError: 'Broken' object has no attribute 'name'

    Overriding __init__ replaces the parent’s — it does not extend it. If you want the parent’s setup, you have to ask for it.

    MRO — the order Python searches
    Child.__mro__  →  [Child, Parent, object]

    Method Resolution Order. Python walks this list left to right and uses the first match. super() does not mean "my parent" — it means "the next class in the MRO", which is why it behaves correctly under multiple inheritance where naming the parent directly does not.

    Worth trying next
    • Override greet() in Child and call super().greet() inside it — extend rather than replace.
    • Add __str__ so print(child1) shows something useful.
    • Give Child two parents and print the MRO — that is where super() earns its design.

    • Python → OOP fundamentals · Python → OOP in Python

  4. 04 — inheritance vs method overriding

    I wrote this thinking it showed method overriding. It runs, but it does not — worth keeping as the contrast, because the distinction is exactly what gets asked.

    class sum:
    def add(self, x, y):
        return x + y

class multiply(sum):
    def multiply(self, x, y):
        return x * y

my_calculation = multiply()
print("Addition:", my_calculation.add(5, 3))
print("Multiplication:", my_calculation.multiply(5, 3))

    Output

    Addition: 8
Multiplication: 15

    Why this is not overriding

    Overriding means the child defines a method with the same name as the parent, replacing it. Here nothing overlaps:

    methods on parent (sum)     : ['add']
methods on child  (multiply): ['multiply']
names defined in BOTH       : none → nothing is overridden

    What it actually shows is inheritance + extension: multiply inherits add and adds a new method beside it. Both calls work — add was simply never replaced.

    Overriding, for comparison
    class Calculator:
    def describe(self):     return "generic calculator"
    def add(self, x, y):    return x + y

class ScientificCalculator(Calculator):
    def describe(self):     return "scientific calculator"   ← overrides
    def power(self, x, y):  return x ** y                    ← extends
    Calculator().describe()            → generic calculator
ScientificCalculator().describe()  → scientific calculator
names in both classes              → {'describe'}
    Override to extend, not just replace
    class Extended(Calculator):
    def describe(self):
        return super().describe() + " (extended)"

Extended().describe()  → "generic calculator (extended)"

    Calling super() inside the override keeps the parent’s behaviour and adds to it — the same idea as super().__init__() in snippet 03.

    Notes
    Two naming problems in the original
    • class sum shadows the builtin. Once that class exists, sum([1, 2, 3]) fails: 
      TypeError: sum() takes no arguments
      Same risk with list, dict, type, id, max.
    • Class and method share the name multiply. Legal, but multiply().multiply() reads badly. PEP 8 wants PascalCase for classes and snake_case for methods, which keeps them visibly different.
    The three words, kept straight
    • Inheritance — the child gets the parent’s methods
    • Overriding — the child redefines a method the parent already has (same name, same class hierarchy)
    • Overloading — several methods with the same name and different signatures. Python does not have it — a second def of the same name simply replaces the first. Use default arguments or *args instead. This is a standard interview trap.
    Related
    • Python → OOP fundamentals · Python → OOP in Python
    • LLD → OOP & SOLID — Liskov substitution is about overriding safely

  5. 05 — method overloading (Python does not have it)

    Two methods with the same name and different parameter counts. In a language with real overloading both would coexist and the call would pick one. In Python the second def simply replaces the first.

    class sum:
    def add(self, x, y):
        return x + y

    def add(self, x, y, z):     # replaces the one above
        return x + y + z

s = sum()
print(s.add(2, 3, 4))

    Output

    9

    The rule, and the proof

    The last definition wins — and the earlier one is gone, not hidden.

    s.add(2, 3, 4)  →  9
s.add(2, 3)     →  TypeError: sum.add() missing 1 required
                   positional argument: 'z'

    That error is the whole point. The two-argument version did not "lose a tie" — it no longer exists. The class body runs top to bottom like ordinary code, and the second def rebinds the name:

    how many 'add' the class holds  →  ['add']      one entry
signature that survived         →  (self, x, y, z)

    A class body is not a declaration — it is a block of statements that builds a namespace. def is an assignment, so defining add twice is no different from writing x = 1 then x = 2.

    Confirmed — the default-argument fix, run
    class sum:
    def add(self, x, y, z=0):
        return x + y + z

s = sum()
print(s.add(2, 3))
    s.add(2, 3)        →  5     z defaults to 0
s.add(2, 3, 4)     →  9     z supplied

s.add(2)           →  TypeError: missing 1 required positional argument: 'y'
s.add(2, 3, 4, 5)  →  TypeError: takes from 3 to 4 positional arguments but 5 were given

    One method, two valid call shapes — which is the behaviour overloading would have given, without overloading existing. The signature is still a single fixed thing:

    inspect.signature(sum.add)  →  (self, x, y, z=0)

    Note the bounds are real: it accepts 2 or 3 arguments and nothing else. Defaults widen the accepted calls, they do not make the method variadic — that is what *args is for.

    Notes
    How to actually get overloading behaviour
    • Default arguments — simplest, and usually right: 
      def add(self, x, y, z=0):
    return x + y + z

add(2, 3)     → 5
add(2, 3, 4)  → 9
    • *args — when the count is genuinely variable: 
      def add(self, *nums):
    return sum(nums)

add(2, 3)        → 5
add(2, 3, 4, 5)  → 14
    • functools.singledispatchmethod — real dispatch, on the type of the first argument: 
      @singledispatchmethod
def add(self, a, b): raise NotImplementedError

@add.register
def _(self, a: int, b: int): return a + b

@add.register
def _(self, a: str, b: str): return a + " " + b

add(2, 3)       → 5
add("a", "b")   → 'a b'
    • typing.overload — declares several signatures for type checkers only. No runtime effect whatsoever; you still write one real implementation.
    Saying it well in an interview

    "Python does not support method overloading. Defining a method twice rebinds the name, so only the last one survives — calling it with the old signature raises a TypeError. The equivalent is default arguments or *args, and functools.singledispatch when you genuinely need to branch on type."

    Overloading is the one of the three that Python lacks — overriding and inheritance both work normally. See snippet 04 for that distinction.

    Also
    • class sum shadows the builtin again — noted in snippet 04. Ironically the *args fix above needs the real sum(), so inside this class it would break.
    • Python → OOP fundamentals · Python → functools

  6. 06 — Serializer vs ModelSerializer

    The same Task serialized two ways. One declares every field and writes create(); the other derives both from the model.

    from rest_framework import serializers
from .models import Task

# fields and create() written by hand
class TaskSerializer(serializers.Serializer):
    title       = serializers.CharField(max_length=100)
    description = serializers.CharField()
    completed   = serializers.BooleanField()

    def create(self, validated_data):
        return Task.objects.create(**validated_data)


# derived from the model
class TaskSerializer(serializers.ModelSerializer):
    class Meta:
        model  = Task
        fields = "__all__"

    Output — both save successfully

    Serializer       is_valid: True  saved: Task object (1)
  → {'title': 'Write tests', 'description': 'for the API', 'completed': False}

ModelSerializer  is_valid: True  saved: Task object (2)
  → {'id': 2, 'title': 'Write tests', 'description': 'for the API', 'completed': False}

    Note the id. The plain Serializer only knows the three fields I typed; ModelSerializer found the primary key too.

    Notes
    What each one actually declared
    PlainTaskSerializer():
    title       = CharField(max_length=100)
    description = CharField()
    completed   = BooleanField()

TaskModelSerializer():
    id          = BigIntegerField(label='ID', read_only=True)
    title       = CharField(max_length=100)
    description = CharField(style={'base_template': 'textarea.html'})
    completed   = BooleanField(required=False)

    Three things it inferred that I did not write: the primary key as read-only, description as a textarea because the model uses TextField, and completed as optional because the model has default=False.

    Where the plain Serializer stops

    I wrote create(), so saving a new object works. Updating one does not:

    ModelSerializer update  →  completed = True
Serializer update       →  NotImplementedError: `update()` must be implemented.

    Both methods are needed, and each has to be written separately. ModelSerializer supplies both.

    The short answer for an interview

    "Serializer requires us to define the fields and usually create()/update() manually, whereas ModelSerializer generates the fields and default create/update behaviour from the Django model."

    Add one sentence on when to use each and it is a complete answer: ModelSerializer for anything backed by a model; plain Serializer when there is no model — a login payload, a search request, a webhook body.

    Careful with fields = "__all__"

    Convenient here, risky in production — add a field to the model and the API silently exposes it. List the fields explicitly once the model has anything private on it.

  7. 07 — parse a key=value string into a dict

    Split on the outer separator, then split each pair on =, then assign. A common warm-up, and the shape of every config, query-string and header parser.

    s = "name=John,age=25,city=Delhi"

result = {}

for i in s.split(","):
    k, v = i.split("=")
    result[k] = v

print(result)

    Output

    {'name': 'John', 'age': '25', 'city': 'Delhi'}

    Step by step

    s.split(",")           →  ['name=John', 'age=25', 'city=Delhi']

'name=John'.split("=") →  ['name', 'John']
'age=25'.split("=")    →  ['age', '25']
'city=Delhi'.split("=")→  ['city', 'Delhi']

    k, v = i.split("=") is tuple unpacking — it requires exactly two parts, which is where this breaks.

    Why it is result and not dict

    My first version named the accumulator dict, which shadows the builtin and breaks it for the rest of the scope:

    dict = {}          # the name now points at your dict
dict(a=1)          →  TypeError: 'dict' object is not callable

    Same trap as class sum in snippet 04, and as input or list. result costs nothing and avoids it.

    The one-line version
    result = {k: v for k, v in (p.split("=") for p in s.split(","))}
  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}
    Notes
    What breaks it — tested
    "name=John,age"       →  ValueError: not enough values to unpack (expected 2, got 1)
"name=John,,age=25"   →  ValueError: not enough values to unpack (expected 2, got 1)
"a=1=2"               →  ValueError: too many values to unpack (expected 2, got 3)

    Three different malformed inputs, three crashes. Real input — a config file, a header, user data — will contain all three eventually.

    The robust version
    def parse(s):
    out = {}
    for pair in s.split(","):
        if "=" not in pair:
            continue                    # skip junk instead of crashing
        k, v = pair.split("=", 1)         # maxsplit=1
        out[k.strip()] = v.strip()      # tolerate spaces
    return out
    "name=John,age=25,city=Delhi"  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}
"name=John,age"                →  {'name': 'John'}          skipped
"a=1=2"                        →  {'a': '1=2'}              value kept whole
" name = John , age = 25 "     →  {'name': 'John', 'age': '25'}  trimmed

    split("=", 1) is the important change. It splits on the first = only, so a value containing = — a base64 string, a password, a query — survives intact instead of raising.

    The stdlib already does this
    from urllib.parse import parse_qsl

dict(parse_qsl("name=John&age=25&city=Delhi"))
  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}

    For query strings specifically, use it — it handles URL encoding, repeated keys and blanks. Write the loop when the format is your own; reach for parse_qsl, configparser or json when it is a standard one.

    Worth noticing
    • Every value is a string. '25', not 25 — convert explicitly if you need a number.
    • Duplicate keys silently overwrite. "a=1,a=2" gives {'a': '2'}; the first is gone.
    • Related: Interview → Convert a string into a list of tuples — the same split-and-restructure pattern.

  8. 08 — find the longest word

    Split into words, track the longest. It printed the right answer — but the logic is wrong, and the test input hid it.

    input = "Django is a powerful framework"
x = input.split()
max = 0
for i in range(len(x)):
    if len(x[i]) > max:
        max = i              # assigns the INDEX, not the length
        result = x[i]
print(result)

    Output

    framework   ✓ correct — by coincidence

    The bug, and why this input hides it

    max is meant to hold the longest length seen so far. max = i stores the position instead, so from then on you are comparing a word length against an array index — two unrelated numbers.

    It survives here because the words happen to get longer towards the end:

    ['Django', 'is', 'a', 'powerful', 'framework']
lengths   6      2    1      8           9        ← increasing at the end

    Change the input and it breaks immediately — tested:

    input                              theirs        correct
'Django is a powerful framework'   'framework'   'framework'   ✓
'aaaa b c'                         'b'           'aaaa'        ✗
'elephant a b c d'                 'a'           'elephant'    ✗
'hello worldwide hi'               'hi'          'worldwide'   ✗
'one two three four'               'four'        'three'       ✗

    Four out of five wrong. Traced on 'aaaa b c':

    i=0  len=4 > max=0  →  max = 0 (the index), result = 'aaaa'
i=1  len=1 > max=0  →  max = 1 (the index), result = 'b'   ← overwritten
i=2  len=1 > max=1? no

    Because max was reset to 0, a one-letter word beat it.

    The one-character fix
    max = len(x[i])      # not max = i
    Cleaner — track the word, not an index
    words = text.split()
best = ""
for word in words:
    if len(word) > len(best):
        best = word

    No index, no second variable to keep in step, no way for them to disagree. Most off-by-one bugs disappear when you stop iterating by index.

    And the one-liner
    max(words, key=len)                  →  'framework'
sorted(words, key=len)[-1]           →  'framework'
max(words, key=len, default=None)    →  None on empty input
    Notes
    Two shadowed builtins here
    • input = "..." breaks input()
    • max = 0 breaks max() — which is the very function that solves this problem in one line

    Third time this has come up: dict in snippet 07, sum in snippet 04, now max and input. Worth making a habit of.

    The real lesson

    A passing test proved nothing here. One input, one correct answer, and a logic error underneath. Pick test cases that could expose the bug — longest word first, all words the same length, a single word, an empty string.

    "".split()                          →  []      loop never runs, result is undefined
max([], key=len)                    →  ValueError
max([], key=len, default=None)      →  None

    The original crashes with NameError on empty input, because result is only assigned inside the if.

    Ties

    > keeps the first longest word; >= would keep the last. max() keeps the first. Say which you intend if asked.
