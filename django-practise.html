  1. 01 — classmethod

    A method bound to the class rather than an instance. It receives cls instead of self, so you can call it without creating an object.

    class MyClass:
    @classmethod
    def displayinfo(cls):
        print("This is MyClass.")

MyClass.displayinfo()

    Output

    This is MyClass.
    Notes
    What to notice
    • No MyClass() anywhere — it is called straight on the class.
    • cls is the class itself, the way self is the instance.
    • It still works if you call it on an instance: MyClass().displayinfo().
    • cls follows the subclass — this is the whole point: 
      class Child(MyClass): pass

MyClass.displayinfo()   # cls is MyClass
Child.displayinfo()     # cls is Child
      which is why classmethods are used for alternative constructors — Model.objects.create(), datetime.fromtimestamp().
    classmethod vs staticmethod vs instance method
    • def m(self) — needs an instance, can read instance state
    • @classmethod def m(cls) — needs the class, can create instances of it
    • @staticmethod def m() — neither; just a function living in the class namespace
    Where you have seen it

    • Interview → What are decorators? — @classmethod is one

  2. 02 — __init__ and instance attributes

    The constructor. It runs when you create an object, and self.name = name is what makes the value stick to that instance.

    class Parent:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print(f"Hello from Parent class. My name is {self.name}.")

p = Parent("Alice")
p.greet()

    Output

    Hello from Parent class. My name is Alice.
    Notes
    What to notice
    • Parent("Alice") calls __init__ automatically — you never call it yourself.
    • self is passed automatically too. p.greet() is really Parent.greet(p).
    • self.name is an instance attribute — each object gets its own. A variable defined directly in the class body would be shared by all of them.
    • __init__ is not really a constructor — __new__ creates the object, __init__ initialises it. Worth knowing if asked.
    The trap worth remembering
    • A mutable default in a signature is created once, at definition time, and shared: 
      def __init__(self, items=[]):   ✗ shared between every instance
def __init__(self, items=None):  ✓
    self.items = items or []
    Next step
    • Add a Child(Parent) and call super().__init__(name) — that is inheritance, and the natural follow-up to this snippet.

  3. 03 — inheritance and super()

    Child extends Parent, adds its own attribute, and calls super().__init__() so the parent’s setup still runs. greet() is never redefined — it is inherited.

    class Parent:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print(f"Hello from Parent class. My name is {self.name}.")


class Child(Parent):
    def __init__(self, name, age):
        super().__init__(name)      # run Parent's __init__ first
        self.age = age


child1 = Child("Khushboo", 10)
child1.greet()

    Output

    Hello from Parent class. My name is Khushboo.
    Notes
    What to notice
    • Child defines no greet(). Python does not find it on Child, looks at Parent, finds it there, and uses it. That is inheritance doing its job.
    • super().__init__(name) runs the parent constructor, which is what sets self.name. Without it, greet() would have nothing to print.
    • Both attributes land on the same object: 
      child1.__dict__  →  {'name': 'Khushboo', 'age': 10}
    • The object is both types at once: 
      isinstance(child1, Child)   → True
isinstance(child1, Parent)  → True
    What happens if you forget super()

    This is the bug worth seeing once, so you recognise it instantly:

    class Broken(Parent):
    def __init__(self, name, age):
        self.age = age          # forgot super().__init__(name)

b = Broken("X", 5)
b.__dict__   →  {'age': 5}      ← no 'name'
b.greet()    →  AttributeError: 'Broken' object has no attribute 'name'

    Overriding __init__ replaces the parent’s — it does not extend it. If you want the parent’s setup, you have to ask for it.

    MRO — the order Python searches
    Child.__mro__  →  [Child, Parent, object]

    Method Resolution Order. Python walks this list left to right and uses the first match. super() does not mean "my parent" — it means "the next class in the MRO", which is why it behaves correctly under multiple inheritance where naming the parent directly does not.

    Worth trying next
    • Override greet() in Child and call super().greet() inside it — extend rather than replace.
    • Add __str__ so print(child1) shows something useful.
    • Give Child two parents and print the MRO — that is where super() earns its design.

    • Python → OOP fundamentals · Python → OOP in Python

  4. 04 — inheritance vs method overriding

    I wrote this thinking it showed method overriding. It runs, but it does not — worth keeping as the contrast, because the distinction is exactly what gets asked.

    class sum:
    def add(self, x, y):
        return x + y

class multiply(sum):
    def multiply(self, x, y):
        return x * y

my_calculation = multiply()
print("Addition:", my_calculation.add(5, 3))
print("Multiplication:", my_calculation.multiply(5, 3))

    Output

    Addition: 8
Multiplication: 15

    Why this is not overriding

    Overriding means the child defines a method with the same name as the parent, replacing it. Here nothing overlaps:

    methods on parent (sum)     : ['add']
methods on child  (multiply): ['multiply']
names defined in BOTH       : none → nothing is overridden

    What it actually shows is inheritance + extension: multiply inherits add and adds a new method beside it. Both calls work — add was simply never replaced.

    Overriding, for comparison
    class Calculator:
    def describe(self):     return "generic calculator"
    def add(self, x, y):    return x + y

class ScientificCalculator(Calculator):
    def describe(self):     return "scientific calculator"   ← overrides
    def power(self, x, y):  return x ** y                    ← extends
    Calculator().describe()            → generic calculator
ScientificCalculator().describe()  → scientific calculator
names in both classes              → {'describe'}
    Override to extend, not just replace
    class Extended(Calculator):
    def describe(self):
        return super().describe() + " (extended)"

Extended().describe()  → "generic calculator (extended)"

    Calling super() inside the override keeps the parent’s behaviour and adds to it — the same idea as super().__init__() in snippet 03.

    Notes
    Two naming problems in the original
    • class sum shadows the builtin. Once that class exists, sum([1, 2, 3]) fails: 
      TypeError: sum() takes no arguments
      Same risk with list, dict, type, id, max.
    • Class and method share the name multiply. Legal, but multiply().multiply() reads badly. PEP 8 wants PascalCase for classes and snake_case for methods, which keeps them visibly different.
    The three words, kept straight
    • Inheritance — the child gets the parent’s methods
    • Overriding — the child redefines a method the parent already has (same name, same class hierarchy)
    • Overloading — several methods with the same name and different signatures. Python does not have it — a second def of the same name simply replaces the first. Use default arguments or *args instead. This is a standard interview trap.
    Related
    • Python → OOP fundamentals · Python → OOP in Python
    • LLD → OOP & SOLID — Liskov substitution is about overriding safely

  5. 05 — method overloading (Python does not have it)

    Two methods with the same name and different parameter counts. In a language with real overloading both would coexist and the call would pick one. In Python the second def simply replaces the first.

    class sum:
    def add(self, x, y):
        return x + y

    def add(self, x, y, z):     # replaces the one above
        return x + y + z

s = sum()
print(s.add(2, 3, 4))

    Output

    9

    The rule, and the proof

    The last definition wins — and the earlier one is gone, not hidden.

    s.add(2, 3, 4)  →  9
s.add(2, 3)     →  TypeError: sum.add() missing 1 required
                   positional argument: 'z'

    That error is the whole point. The two-argument version did not "lose a tie" — it no longer exists. The class body runs top to bottom like ordinary code, and the second def rebinds the name:

    how many 'add' the class holds  →  ['add']      one entry
signature that survived         →  (self, x, y, z)

    A class body is not a declaration — it is a block of statements that builds a namespace. def is an assignment, so defining add twice is no different from writing x = 1 then x = 2.

    Confirmed — the default-argument fix, run
    class sum:
    def add(self, x, y, z=0):
        return x + y + z

s = sum()
print(s.add(2, 3))
    s.add(2, 3)        →  5     z defaults to 0
s.add(2, 3, 4)     →  9     z supplied

s.add(2)           →  TypeError: missing 1 required positional argument: 'y'
s.add(2, 3, 4, 5)  →  TypeError: takes from 3 to 4 positional arguments but 5 were given

    One method, two valid call shapes — which is the behaviour overloading would have given, without overloading existing. The signature is still a single fixed thing:

    inspect.signature(sum.add)  →  (self, x, y, z=0)

    Note the bounds are real: it accepts 2 or 3 arguments and nothing else. Defaults widen the accepted calls, they do not make the method variadic — that is what *args is for.

    Notes
    How to actually get overloading behaviour
    • Default arguments — simplest, and usually right: 
      def add(self, x, y, z=0):
    return x + y + z

add(2, 3)     → 5
add(2, 3, 4)  → 9
    • *args — when the count is genuinely variable: 
      def add(self, *nums):
    return sum(nums)

add(2, 3)        → 5
add(2, 3, 4, 5)  → 14
    • functools.singledispatchmethod — real dispatch, on the type of the first argument: 
      @singledispatchmethod
def add(self, a, b): raise NotImplementedError

@add.register
def _(self, a: int, b: int): return a + b

@add.register
def _(self, a: str, b: str): return a + " " + b

add(2, 3)       → 5
add("a", "b")   → 'a b'
    • typing.overload — declares several signatures for type checkers only. No runtime effect whatsoever; you still write one real implementation.
    Saying it well in an interview

    "Python does not support method overloading. Defining a method twice rebinds the name, so only the last one survives — calling it with the old signature raises a TypeError. The equivalent is default arguments or *args, and functools.singledispatch when you genuinely need to branch on type."

    Overloading is the one of the three that Python lacks — overriding and inheritance both work normally. See snippet 04 for that distinction.

    Also
    • class sum shadows the builtin again — noted in snippet 04. Ironically the *args fix above needs the real sum(), so inside this class it would break.
    • Python → OOP fundamentals · Python → functools

  6. 06 — Serializer vs ModelSerializer

    The same Task serialized two ways. One declares every field and writes create(); the other derives both from the model.

    from rest_framework import serializers
from .models import Task

# fields and create() written by hand
class TaskSerializer(serializers.Serializer):
    title       = serializers.CharField(max_length=100)
    description = serializers.CharField()
    completed   = serializers.BooleanField()

    def create(self, validated_data):
        return Task.objects.create(**validated_data)


# derived from the model
class TaskSerializer(serializers.ModelSerializer):
    class Meta:
        model  = Task
        fields = "__all__"

    Output — both save successfully

    Serializer       is_valid: True  saved: Task object (1)
  → {'title': 'Write tests', 'description': 'for the API', 'completed': False}

ModelSerializer  is_valid: True  saved: Task object (2)
  → {'id': 2, 'title': 'Write tests', 'description': 'for the API', 'completed': False}

    Note the id. The plain Serializer only knows the three fields I typed; ModelSerializer found the primary key too.

    Notes
    What each one actually declared
    PlainTaskSerializer():
    title       = CharField(max_length=100)
    description = CharField()
    completed   = BooleanField()

TaskModelSerializer():
    id          = BigIntegerField(label='ID', read_only=True)
    title       = CharField(max_length=100)
    description = CharField(style={'base_template': 'textarea.html'})
    completed   = BooleanField(required=False)

    Three things it inferred that I did not write: the primary key as read-only, description as a textarea because the model uses TextField, and completed as optional because the model has default=False.

    Where the plain Serializer stops

    I wrote create(), so saving a new object works. Updating one does not:

    ModelSerializer update  →  completed = True
Serializer update       →  NotImplementedError: `update()` must be implemented.

    Both methods are needed, and each has to be written separately. ModelSerializer supplies both.

    The short answer for an interview

    "Serializer requires us to define the fields and usually create()/update() manually, whereas ModelSerializer generates the fields and default create/update behaviour from the Django model."

    Add one sentence on when to use each and it is a complete answer: ModelSerializer for anything backed by a model; plain Serializer when there is no model — a login payload, a search request, a webhook body.

    Careful with fields = "__all__"

    Convenient here, risky in production — add a field to the model and the API silently exposes it. List the fields explicitly once the model has anything private on it.

  7. 07 — parse a key=value string into a dict

    Split on the outer separator, then split each pair on =, then assign. A common warm-up, and the shape of every config, query-string and header parser.

    s = "name=John,age=25,city=Delhi"

result = {}

for i in s.split(","):
    k, v = i.split("=")
    result[k] = v

print(result)

    Output

    {'name': 'John', 'age': '25', 'city': 'Delhi'}

    Step by step

    s.split(",")           →  ['name=John', 'age=25', 'city=Delhi']

'name=John'.split("=") →  ['name', 'John']
'age=25'.split("=")    →  ['age', '25']
'city=Delhi'.split("=")→  ['city', 'Delhi']

    k, v = i.split("=") is tuple unpacking — it requires exactly two parts, which is where this breaks.

    Why it is result and not dict

    My first version named the accumulator dict, which shadows the builtin and breaks it for the rest of the scope:

    dict = {}          # the name now points at your dict
dict(a=1)          →  TypeError: 'dict' object is not callable

    Same trap as class sum in snippet 04, and as input or list. result costs nothing and avoids it.

    The one-line version
    result = {k: v for k, v in (p.split("=") for p in s.split(","))}
  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}
    Notes
    What breaks it — tested
    "name=John,age"       →  ValueError: not enough values to unpack (expected 2, got 1)
"name=John,,age=25"   →  ValueError: not enough values to unpack (expected 2, got 1)
"a=1=2"               →  ValueError: too many values to unpack (expected 2, got 3)

    Three different malformed inputs, three crashes. Real input — a config file, a header, user data — will contain all three eventually.

    The robust version
    def parse(s):
    out = {}
    for pair in s.split(","):
        if "=" not in pair:
            continue                    # skip junk instead of crashing
        k, v = pair.split("=", 1)         # maxsplit=1
        out[k.strip()] = v.strip()      # tolerate spaces
    return out
    "name=John,age=25,city=Delhi"  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}
"name=John,age"                →  {'name': 'John'}          skipped
"a=1=2"                        →  {'a': '1=2'}              value kept whole
" name = John , age = 25 "     →  {'name': 'John', 'age': '25'}  trimmed

    split("=", 1) is the important change. It splits on the first = only, so a value containing = — a base64 string, a password, a query — survives intact instead of raising.

    The stdlib already does this
    from urllib.parse import parse_qsl

dict(parse_qsl("name=John&age=25&city=Delhi"))
  →  {'name': 'John', 'age': '25', 'city': 'Delhi'}

    For query strings specifically, use it — it handles URL encoding, repeated keys and blanks. Write the loop when the format is your own; reach for parse_qsl, configparser or json when it is a standard one.

    Worth noticing
    • Every value is a string. '25', not 25 — convert explicitly if you need a number.
    • Duplicate keys silently overwrite. "a=1,a=2" gives {'a': '2'}; the first is gone.
    • Related: Interview → Convert a string into a list of tuples — the same split-and-restructure pattern.

  8. 08 — find the longest word

    Split into words, track the longest. It printed the right answer — but the logic is wrong, and the test input hid it.

    input = "Django is a powerful framework"
x = input.split()
max = 0
for i in range(len(x)):
    if len(x[i]) > max:
        max = i              # assigns the INDEX, not the length
        result = x[i]
print(result)

    Output

    framework   ✓ correct — by coincidence

    The bug, and why this input hides it

    max is meant to hold the longest length seen so far. max = i stores the position instead, so from then on you are comparing a word length against an array index — two unrelated numbers.

    It survives here because the words happen to get longer towards the end:

    ['Django', 'is', 'a', 'powerful', 'framework']
lengths   6      2    1      8           9        ← increasing at the end

    Change the input and it breaks immediately — tested:

    input                              theirs        correct
'Django is a powerful framework'   'framework'   'framework'   ✓
'aaaa b c'                         'b'           'aaaa'        ✗
'elephant a b c d'                 'a'           'elephant'    ✗
'hello worldwide hi'               'hi'          'worldwide'   ✗
'one two three four'               'four'        'three'       ✗

    Four out of five wrong. Traced on 'aaaa b c':

    i=0  len=4 > max=0  →  max = 0 (the index), result = 'aaaa'
i=1  len=1 > max=0  →  max = 1 (the index), result = 'b'   ← overwritten
i=2  len=1 > max=1? no

    Because max was reset to 0, a one-letter word beat it.

    The one-character fix
    max = len(x[i])      # not max = i
    Cleaner — track the word, not an index
    words = text.split()
best = ""
for word in words:
    if len(word) > len(best):
        best = word

    No index, no second variable to keep in step, no way for them to disagree. Most off-by-one bugs disappear when you stop iterating by index.

    And the one-liner
    max(words, key=len)                  →  'framework'
sorted(words, key=len)[-1]           →  'framework'
max(words, key=len, default=None)    →  None on empty input
    Notes
    Two shadowed builtins here
    • input = "..." breaks input()
    • max = 0 breaks max() — which is the very function that solves this problem in one line

    Third time this has come up: dict in snippet 07, sum in snippet 04, now max and input. Worth making a habit of.

    The real lesson

    A passing test proved nothing here. One input, one correct answer, and a logic error underneath. Pick test cases that could expose the bug — longest word first, all words the same length, a single word, an empty string.

    "".split()                          →  []      loop never runs, result is undefined
max([], key=len)                    →  ValueError
max([], key=len, default=None)      →  None

    The original crashes with NameError on empty input, because result is only assigned inside the if.

    Ties

    > keeps the first longest word; >= would keep the last. max() keeps the first. Say which you intend if asked.

  9. 09 — reverse the words in a string

    Split into words, reverse the list, join back into a string. The corrected version — my first attempt stopped at [::-1] and left a list.

    input = "I love Python"
# output = "Python love I"

x = " ".join(input.split()[::-1])
print(x)

    Output

    Python love I   ✓

    The three steps

    input.split()          →  ['I', 'love', 'Python']     string  → list
[::-1]                 →  ['Python', 'love', 'I']     list    → reversed list
" ".join(...)          →  'Python love I'             list    → string

    Each does one job, and the join is the step that is easy to forget — without it you print a list, not a sentence.

    Free bonus: messy whitespace just works
    "   I   love   Python   "
  → same code →  'Python love I'

    split() with no argument collapses runs of whitespace and strips the ends, so no cleanup is needed. split(" ") would have produced a list full of empty strings.

    Notes
    Why [::-1] behaves differently on each
    "I love Python"[::-1]     →  'nohtyP evol I'          characters
['I','love','Python'][::-1] →  ['Python','love','I']   elements

    Same syntax, and a slice always returns the type it was given. That is the whole reason the two attempts differ.

    input shadows the builtin — again

    Fourth time in this log after sum, dict and max. text or s costs nothing.

  10. 10 — find the student with the highest marks

    Same shape as snippet 08, and this time the logic is right — it stores the value, not the position.

    marks = {
    "John": 70,
    "Alice": 92,
    "Bob": 85
}

max = 0
for key, value in marks.items():
    if value > max:
        student = key
        max = value          # the VALUE — this is the fix

print(student)

    Output

    Alice   ✓

    Trace

    John=70  > max=0   →  student=John,  max=70
Alice=92 > max=70  →  student=Alice, max=92
Bob=85   > max=92? no
    Compare with snippet 08
    08:  max = i        ← the index     ✗ compares a length against a position
10:  max = value    ← the value     ✓ compares like with like

    Identical structure, one line different, and that line is the whole difference between working and accidentally-working. Good instinct to keep the accumulator and the comparison in the same units.

    .items() is what makes it readable
    for key, value in marks.items():   both at once  ✓
for key in marks:                  keys only, then marks[key]
for value in marks.values():       values only — loses the name
    Notes
    The one-liners
    max(marks, key=marks.get)                 →  'Alice'
max(marks.items(), key=lambda x: x[1])    →  ('Alice', 92)    name and mark
sorted(marks.items(), key=lambda x: -x[1])
  →  [('Alice', 92), ('Bob', 85), ('John', 70)]               full ranking

    key=marks.get tells max to compare by the dict’s values while still returning the key.

    Two edge cases the loop gets wrong — tested

    Empty dict — the loop never runs, so student is never assigned:

    marks = {}
print(student)  →  NameError: name 'student' is not defined

    Negative values — starting at max = 0 assumes every mark is positive:

    {"A": -5, "B": -2}
  loop        →  None   nothing ever beats 0
  max(key=..) →  'B'    correct

    Fine for marks, wrong for temperatures, balances or profit/loss. Starting from float("-inf"), or from the first item, avoids the assumption entirely.

    max(marks, key=marks.get, default=None)   →  None on an empty dict
    Ties
    {"A": 90, "B": 90}  →  'A'

    > keeps the first; >= would keep the last. max() also keeps the first. Worth stating which you intend if asked — "who scored highest" is ambiguous when two people did.

    And again

    max = 0 shadows the builtin — fifth time in this log after sum, dict, max and input. It is also the function that solves this in one line.

  11. 11 — group a list by a key

    Split each entry, then collect names under their role. The if/else exists to create the list the first time a role appears.

    employees = [
    "John:Developer",
    "Alice:Manager",
    "Bob:Developer",
    "David:Manager",
    "Sam:Tester"
]

res = {}
for emp in employees:
    key, value = emp.split(":")
    if value in res:
        res[value].append(key)
    else:
        res[value] = [key]

print(res)

    Output

    {'Developer': ['John', 'Bob'],
 'Manager':   ['Alice', 'David'],
 'Tester':    ['Sam']}   ✓

    What the if/else is protecting against

    Drop it and the very first employee crashes — you cannot append to a list that does not exist yet:

    res[value].append(key)      # no check
  →  KeyError: 'Developer'

    That "create it if missing, otherwise append" shape is so common Python has two shortcuts for it.

    defaultdict — the idiomatic version
    from collections import defaultdict

res = defaultdict(list)
for emp in employees:
    key, value = emp.split(":")
    res[value].append(key)      # no check needed

    A missing key auto-creates an empty list, so the branch disappears. Wrap in dict(res) at the end if you want a plain dict back.

    setdefault — same idea, no import
    res.setdefault(value, []).append(key)

    Returns the existing list, or inserts [] and returns that. One line, works on an ordinary dict.

    All three produce identical output — verified.

    Notes
    Order is preserved, twice over
    keys, in order first seen :  ['Developer', 'Manager', 'Tester']
Developer’s list           :  ['John', 'Bob']   input order kept

    Dicts have kept insertion order since Python 3.7, so grouping does not scramble anything.

    The groupby trap

    itertools.groupby looks like the right tool and is not, unless you sort first:

    groupby(pairs, key=role)            →  {'Developer': ['Bob'], 'Manager': ['David'], 'Tester': ['Sam']}
groupby(sorted(pairs, key=role), …) →  {'Developer': ['John','Bob'], …}

    It groups consecutive runs, not equal values. Unsorted input silently loses data — note John and Alice vanished above, with no error. The dict approach needs no sort and is O(n) rather than O(n log n).

    Malformed input
    "NoColon".split(":")  →  ValueError: not enough values to unpack (expected 2, got 1)
"A:B:C".split(":")    →  ValueError: too many values to unpack (expected 2, got 3)
"A:B:C".split(":", 1) →  ['A', 'B:C']

    Same lesson as snippet 07: maxsplit=1 plus a guard makes it survive real data.

    Inverting instead of grouping

    If each key mapped to exactly one value you would write res[value] = key — but that overwrites duplicates. The list is what makes it a grouping rather than an inversion, and that distinction is the point of the exercise.

  12. 12 — flatten a list of pairs

    Unpack each inner list into two names, append both. It works — but the unpacking quietly assumes every inner list has exactly two items.

    nums = [[1, 2], [3, 4], [5, 6]]
x = []

for key, value in nums:
    x.append(key)
    x.append(value)

print(x)

    Output

    [1, 2, 3, 4, 5, 6]   ✓

    What for key, value in nums is really doing

    [1, 2]  →  key=1, value=2
[3, 4]  →  key=3, value=4
[5, 6]  →  key=5, value=6

    Python unpacks each inner list into two names in one step — the same tuple unpacking as k, v = pair, written into the for.

    Which means it only works for pairs
    [[1,2], [3]]       →  ValueError: not enough values to unpack (expected 2, got 1)
[[1,2], [3,4,5]]   →  ValueError: too many values to unpack (expected 2, got 3)

    If the job is "flatten", that restriction is accidental — nothing about flattening requires pairs. It shows up the first time the data is ragged.

    The general version
    x = [n for pair in nums for n in pair]

    Reads in the same order you would write the loops — outer first, then inner. Works on any shape:

    [[1,2,3], [4], [5,6]]
  comprehension →  [1, 2, 3, 4, 5, 6]
  for k, v in … →  ValueError
    Notes
    Four ways, all giving [1, 2, 3, 4, 5, 6]
    [n for pair in nums for n in pair]              comprehension  ← default
list(itertools.chain(*nums))                   unpacks the outer list
list(itertools.chain.from_iterable(nums))      no unpacking, works on generators
sum(nums, [])                                  works, but do not
    Why not sum(nums, [])

    It builds a brand-new list on every addition, so it is O(n²). Measured on 2,000 pairs:

    comprehension   0.011s
sum(list, [])   0.697s     ×66 slower

    Fine on six items, a real problem on sixty thousand. It is the classic "clever one-liner that does not scale".

    It only flattens ONE level
    [[1, [2, 3]], [4, [5, 6]]]
  →  [1, [2, 3], 4, [5, 6]]   inner lists survive

    Arbitrary depth needs recursion. Worth saying out loud if asked to "flatten a nested list" — the first question is how deep.

    When the pair unpacking is the right choice

    Not here, but it is exactly right when the two items mean something different — for name, role in pairs. The names document the data. Using key, value for numbers being flattened is a small mismatch: they are not keys and values, just items.

  13. 13 — sum each inner list

    Walk the rows, keep a running total per row, append it. It works — but the accumulator is named sum, which is the exact builtin that would have replaced the whole inner loop.

    nums = [
    [1, 2, 3],
    [4, 5],
    [6, 7, 8, 9]
]
res = []
for i in nums:
    sum = 0
    for j in i:
        sum = sum + j
    res.append(sum)

print(res)

    Output

    [6, 9, 30]   ✓

    sum = 0 deletes the tool you needed

    sum is a builtin. Assigning to it replaces it for the rest of the module — not just inside the loop:

    for i in nums:
    sum = 0          ← builtin sum is gone from here on
    ...

print(sum(nums[0]))
TypeError: 'int' object is not callable

    Python is not confused — sum really is 30 by then, and you cannot call 30. The irony is the point: the builtin this code shadows is the one that does this job in one call.

    Same answer, builtin intact
    res = [sum(row) for row in nums]

[6, 9, 30]

    And it is faster — sum loops in C, the manual version loops in Python. Measured on 1,000 rows of 100 ints:

    manual loop   0.774 ms
[sum(row) …]  0.184 ms     ×4.2 faster
    Names that say what the thing is
    for i in nums:        i reads as an index — it is a row (a list)
    for j in i:       j reads as an index — it is a number

for row in nums:      now the code says what it holds
    for n in row:

    i and j are a convention for indices (for i in range(len(x))). Using them for the items themselves is the one place they mislead.

    Notes
    Row totals vs grand total
    [sum(row) for row in nums]              → [6, 9, 30]     per row
sum(sum(row) for row in nums)           → 45             everything
sum(itertools.chain.from_iterable(nums)) → 45            same, one pass

    Interviewers often ask for one and then the other. Knowing both is the whole answer.

    Empty rows are already handled
    [[1,2], [], [3]]  →  [3, 0, 3]

    sum([]) is 0, and the manual loop starts at 0 too — both give the same thing. No special case needed.

    sum is numbers only
    sum(["a", "b"])
TypeError: unsupported operand type(s) for +: 'int' and 'str'

"".join(["a", "b"])   →  "ab"

    It starts from 0, so the first + is 0 + "a". Strings concatenate with join, not sum.

    The shadowing pattern, again

    This is the same bug shape as class sum in snippet 04, max = i in snippet 08, and dict = {} in snippet 07. Nothing warns you — the name is simply gone until the module ends. Reaching for total, best, result, counts costs nothing and keeps the builtin.

  14. 14 — try / except, and why a bare except is the wrong default exception handling

    Divide by zero, catch it, keep going. It works — but except: with nothing after it catches everything, including the things you never wanted to catch.

    a = 10
b = 0
try:
    print(a / b)
except:
    print("something is wrong")

    Output

    something is wrong   ✓

    What a bare except also swallows

    except:              catches ZeroDivisionError   wanted
                     catches NameError           a typo you will never find
                     catches KeyboardInterrupt   Ctrl-C stops working
                     catches SystemExit          the process refuses to exit

    The real cost is not the exotic ones — it is that a misspelled variable inside the try now prints "something is wrong" instead of telling you the name is undefined. The bug hides behind your own error message.

    Name the error you expect
    try:
    print(a / b)
except ZeroDivisionError:
    print("b cannot be zero")

    Now anything else going wrong still crashes loudly — which is what you want, because you did not plan for it.

    Keep the message
    except ZeroDivisionError as e:
    print("failed:", e)

failed: division by zero

    "something is wrong" tells you nothing at 2am. The exception already carries a precise message — print it.

    Notes
    If you genuinely must catch everything
    except Exception:          everything normal, but NOT Ctrl-C / SystemExit
except:                    literally everything

    KeyboardInterrupt and SystemExit inherit from BaseException, not Exception — which is exactly why that split exists.

    Only wrap the line that can fail
    try:
    value = a / b          one risky line
except ZeroDivisionError:
    value = 0
print(value)               outside — cannot be swallowed

    A large try block quietly protects lines you never meant to protect.

  15. 15 — catching a specific KeyError exception handling

  16. 16 — raising your own exception exception handling

    Raise an error when the withdrawal is bigger than the balance. The raise is right — but nothing catches it, and the brief also asked for non-numeric amounts to be handled.

    def amount(balance, withdrawal_amount):
    if withdrawal_amount > balance:
        raise Exception("Insufficient balance")
    amount_left = balance - withdrawal_amount
    return amount_left

print(amount(1000, 5000))

    Output

    7000                                    ✓ first call
Traceback (most recent call last):
  ...

    Raising is only half of it

    The function correctly refuses the withdrawal. But an uncaught exception ends the process — the second print never runs, and anything after it never runs either. Raising says "I will not do this"; someone still has to decide what happens next.

    try:
    print(amount(1000, 5000))
except ValueError as e:
    print("Withdrawal refused:", e)

Withdrawal refused: Insufficient balance   program continues
    The missing requirement: non-numeric amounts
    amount(1000, "abc")
TypeError: '>' not supported between instances of 'str' and 'int'

    def amount(balance, withdrawal_amount):
    if isinstance(withdrawal_amount, bool) or not isinstance(withdrawal_amount, (int, float)):
        raise TypeError("Amount must be a number")
    if withdrawal_amount <= 0:
        raise ValueError("Amount must be positive")
    if withdrawal_amount > balance:
        raise ValueError("Insufficient balance")
    return balance - withdrawal_amount
    raise Exception(...) is too broad
    raise Exception("Insufficient balance")   only catchable as except Exception
raise ValueError("Insufficient balance")  a caller can catch just this

    Why isinstance(x, bool) is checked separately
    isinstance(True, int)   →  True   bool subclasses int in Python

    class InsufficientBalance(ValueError):

  17. 17 — employee leave management exception handling

    Six rules: reject unknown employees, non-numeric days, zero or negative days and over-drawn leave; otherwise deduct and return the balance. The checks are all correct — but catching the errors inside the function cancels out the raise, and rule 2 is not implemented.

    employees = {"John": 10, "Alice": 5, "Bob": 8}

def apply_leave(employees, employee_name, days):
    try:
        if employee_name not in employees:
            raise ValueError("Employee not found")

        if days <= 0:
            raise ValueError("Invalid leave days")

        if days > employees[employee_name]:
            raise ValueError("Insufficient leave balance")

        employees[employee_name] = employees[employee_name] - days
        return employees[employee_name]

    except ValueError as e:
        print(e)

leave_left = apply_leave(employees, "John", 3)
print("Leave left:", leave_left)

    Output

    Leave left: 7   ✓ the happy path is correct

    The failure paths are where it breaks

    apply_leave(employees, "Zara", 2)
  prints  Employee not found
  returns None        →  "Leave left: None"

apply_leave(employees, "Alice", 99)
  prints  Insufficient leave balance
  returns None        →  "Leave left: None"

    A function that hits except and only prints falls off the end, and falling off the end returns None. So "Leave left: None" reads like a successful call for an employee with no leave — the caller has no way to tell the difference between refused and zero.

    Raising and catching in the same function cancel out
    raise ValueError("Employee not found")   ← says "I refuse, caller decide"
except ValueError as e: print(e)         ← "never mind, I handled it"

    Rule 1 says raise an exception. Wrapped in its own try, nothing ever escapes the function, so from outside it never raises at all. Raise in the function, catch at the caller — that separation is the entire point of exceptions.

    Rule 2 is missing, and it crashes
    apply_leave(employees, "Bob", "three")
TypeError: '<=' not supported between instances of 'str' and 'int'

    A TypeError is not a ValueError, so except ValueError does not catch it — the program dies on exactly the input the brief told you to handle. The comparison fails before any check runs, so the type has to be tested first.

    The version that satisfies all six rules
    def apply_leave(employees, employee_name, days):
    if employee_name not in employees:
        raise ValueError("Employee not found")

    if isinstance(days, bool) or not isinstance(days, (int, float)):
        raise TypeError("Days must be a number")

    if days <= 0:
        raise ValueError("Invalid leave days")

    if days > employees[employee_name]:
        raise ValueError("Insufficient leave balance")

    employees[employee_name] -= days
    return employees[employee_name]


# the caller decides what a failure means
try:
    left = apply_leave(employees, "John", 3)
    print("Leave left:", left)
except TypeError:
    print("Days must be a number")
except ValueError as e:
    print("Could not apply leave:", e)

    No try inside the function at all. It either returns a real number or raises — never None.

    Every case, run
    ("John",  3)        →  Leave left: 7                                ✓
("Zara",  2)        →  Could not apply leave: Employee not found
("John",  0)        →  Could not apply leave: Invalid leave days
("John", -5)        →  Could not apply leave: Invalid leave days
("Alice", 99)       →  Could not apply leave: Insufficient leave balance
("Bob",  "three")   →  Days must be a number                        rule 2, no crash
("Bob",  True)      →  Days must be a number
("Bob",  None)      →  Days must be a number
("Bob",  2.5)       →  Leave left: 5.5                              half days work
    Notes
    One thing the original gets right

    The deduction is the last statement. Every check runs before the dictionary is touched, so a refused request leaves the balance untouched — Alice still has 5 after asking for 99. Validate first, mutate last: get that order wrong and a failed call silently corrupts your data.

    True is a number to Python
    isinstance(True, int)          →  True
apply_leave(emp, "Bob", True)  →  deducts 1 day   without the bool check
    Mutating the caller's dictionary
    employees[employee_name] -= days

    The dict is changed in place, so the caller's copy changes too — correct here, since the brief says to deduct. Worth saying out loud in an interview: it means the function has a side effect, and a side effect plus a returned value is two jobs. The alternative is returning a new dict and leaving the original alone.

    Why not just return an error string?
    return "Employee not found"    caller must remember to check
raise ValueError(...)          caller cannot ignore it by accident

    A returned error is easy to drop on the floor — which is exactly what "Leave left: None" is. An exception stops the program until someone deals with it.

  18. 18 — public, protected and private oop

    Python has no public, private or protected keywords. It has two naming conventions and one piece of actual machinery — and this snippet shows the gap between them.

    class employee:
  def __init__(self, emp_name, emp_department):
    self._emp_name = emp_name
    self.emp_department = emp_department

class manager(employee):
  pass

e1 = manager('khushboo', 'tecops')
print(e1)
print(e1._emp_name)
print(e1.emp_department)

    Output

    <__main__.manager object at 0x104d95fd0>
khushboo      ← the "protected" one printed from outside, no complaint
tecops

    The three levels

    self.emp_department     public      use it anywhere
self._emp_name          protected   convention only — nothing stops you
self.__salary           private     name-mangled, still not sealed

    Your own last two lines are the proof: e1._emp_name printed happily. The underscore is a message to the next developer — "this is internal, do not rely on it" — not a lock. Python's phrasing for this is "we are all consenting adults here".

    What the double underscore actually does
    class Employee:
    def __init__(self, name, dept):
        self.name     = name
        self._dept    = dept
        self.__salary = 50000

e = Employee("khushboo", "techops")

e.name       →  'khushboo'
e._dept      →  'techops'   works anyway
e.__salary   →  AttributeError: 'Employee' object has no attribute '__salary'

    Looks private — until you see what is really stored:

    vars(e)  →  ['name', '_dept', '_Employee__salary']

e._Employee__salary  →  50000

    Python renamed it to _ClassName__attr. That is name mangling, not access control. Nothing is hidden; the label just changed.

    So why does __ exist at all?

    To stop a subclass accidentally overwriting a parent's attribute — a name collision, not an intruder:

    class Base:
    def __init__(self):
        self.__state = "base state"    # becomes _Base__state
        self._open   = "base open"

class Child(Base):
    def __init__(self):
        super().__init__()
        self.__state = "child state"   # becomes _Child__state — its own slot
        self._open   = "child open"    # SAME slot — parent's value is gone

c = Child()
Base still sees:  ('base state', 'child open')
all slots:        ['_Base__state', '_open', '_Child__state']

    The __ attribute survived the subclass; the _ one was silently clobbered. That is the entire reason to reach for __ — and it only matters when you are writing a base class others will inherit from.

    The cost: your own subclass cannot read it
    class Manager(Employee):
    def show(self): return self.__code     # Python looks for _Manager__code

AttributeError: 'Manager' object has no attribute '_Manager__code'

    Mangling uses the class the code is written in, not the object's class — so Manager asks for _Manager__code while the value sits in _Employee__code. If subclasses should see it, use one underscore. This is precisely why _ is the common choice and __ is rare.

    Notes
    print(e1) and that memory address
    <__main__.manager object at 0x104d95fd0>

    Not an error — just the default __repr__, which has nothing useful to say. Give the class one:

    def __repr__(self):
    return f"Manager({self._emp_name!r}, {self.emp_department!r})"

print(e1)  →  Manager('khushboo', 'tecops')

    Worth doing on any class you will debug, which is all of them. __repr__ is for you; __str__ is for the user.

    Real access control: property

    If you want a rule enforced rather than suggested, a property is the tool — the attribute stays public, the rule runs on assignment:

    class Account:
    def __init__(self, balance): self._balance = balance

    @property
    def balance(self): return self._balance

    @balance.setter
    def balance(self, v):
        if v < 0: raise ValueError("balance cannot be negative")
        self._balance = v

a.balance        →  100
a.balance = 250  →  250
a.balance = -5   →  ValueError: balance cannot be negative

    Callers still write a.balance. You added validation without changing a single line that uses the class — which is why Python has no getters and setters by default.

    Compared to Java and C++
    Java/C++   private   compiler refuses to compile
Python     __attr    renamed; reachable if you insist
Python     _attr     documentation, enforced by nobody

    Say this plainly in an interview. "Python has no true private" is the correct answer, and explaining mangling vs enforcement is what separates it from a memorised one.

    Naming
    class employee:    reads like a variable
class Employee:    PEP 8 — classes are CapWords

    Same for manager → Manager. It is cosmetic, but every Python codebase follows it, so breaking it is noticeable.

    Snippet 18 with one line added: company_name sits in the class body, not on self. All three ways of reading it give the same answer — and that hides where it actually lives.

    class employee:
  company_name = 'abc'                      ← class variable, one copy

  def __init__(self, emp_name, emp_department):

    <__main__.manager object at 0x101055fd0>

tecops

    Three reads, one object

    vars(e1)        →  {'_emp_name': 'khushboo', 'emp_department': 'tecops'}

vars(employee)  →  {'company_name': 'abc'}    it lives here

    Attribute lookup walks instance → class → base classes and stops at the first hit. e1.company_name finds nothing on e1, nothing on manager, then finds it on employee. Nothing was copied anywhere — all three names point at one string.

    Writing through the instance does not write to the class
    e1.company_name = 'xyz'

e2.company_name        →  'abc'   another instance is unaffected
employee.company_name  →  'abc'   the class never changed

    Writing through the class changes everyone
    employee.company_name = 'newco'

    manager.company_name = 'mgmt-co'

employee → newco      parent untouched
e1       → mgmt-co    because e1 is a manager
    Notes
    The trap: a mutable class variable is genuinely shared
    class Team:
    members = []                       one list for the entire class
    def add(self, who): self.members.append(who)

a = Team('alpha'); b = Team('beta')

a.members  →  ['khushboo', 'asha']
b.members  →  ['khushboo', 'asha']
a.members is b.members is Team.members  →  True

    A string is immutable, so company_name never shows this. A list is not — .append() mutates the one shared object instead of rebinding, so every instance sees it. The fix is to create it per object:

    def __init__(self, name):
    self.name = name
    self.members = []       a2 → ['khushboo']   b2 → ['asha']

    Rule of thumb: a class variable is safe when it is a constant — a string, a number, a tuple. The moment it is a list, dict or set, move it into __init__.

    += behaves differently depending on the type
    class C:
    nums  = [1]
    count = 0

c.nums  += [2]      in-place extend  →  mutates the class list
c.count += 1        rebind           →  creates an instance attribute

C.nums  → [1, 2]    c.nums  → [1, 2]      class changed
C.count → 0         c.count → 1           class untouched

    Same operator, same syntax, opposite outcome — because += on a list calls __iadd__ and mutates, while on an int it can only rebind. Worth knowing before you debug it at 2am.

    When class variables are the right tool
    class Order:
    TAX_RATE   = 0.18          a constant every order shares
    STATUSES   = ("new", "paid", "shipped")
    order_count = 0            a counter, updated via the CLASS

    def __init__(self):
        Order.order_count += 1     Order., not self. — self. would shadow

  20. 20 — the getter, and why Python usually does not need one oop

    A mangled attribute plus a method to read it — the Java shape, written in Python. It runs, but the getter is not buying what it looks like it is buying.

    class Account:
    def __init__(self, balance):
        self.__balance = balance

    def get_balance(self):
        return self.__balance


a = Account(5000)

print(a.get_balance())

    Output

    5000   ✓

    What the getter actually provides

    returns the value unchanged     no transformation
runs no validation              Account(-5000) is accepted
has no matching setter          yet the value can still be changed

    All three, measured:

    Account(-5000).get_balance()   →  -5000        __init__ never checked

a._Account__balance = -999
a.get_balance()                →  -999         no setter, changed anyway

    The __ is name mangling, not privacy (snippet 18) — so the balance is neither validated nor read-only. The getter is a layer of ceremony around a plain attribute read.

    The Python version of the same class
    class Account:
    def __init__(self, balance):
        self.balance = balance

a.balance   →  5000

    Shorter, and gives up nothing — because of what comes next.

    The real argument: adding a rule later costs zero callers

    In Java you write getters up front, since switching a public field to a method later breaks every caller. In Python a @property keeps the attribute syntax, so the rule can arrive on the day you need it:

    class Account:
    def __init__(self, balance):
        self.balance = balance          goes through the setter too

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, v):
        if not isinstance(v, (int, float)) or isinstance(v, bool):
            raise TypeError("balance must be a number")
        if v < 0:
            raise ValueError("balance cannot be negative")
        self._balance = v
    a.balance          →  5000          identical syntax, callers untouched
a.balance = -1     →  ValueError: balance cannot be negative
a.balance = "abc"  →  TypeError: balance must be a number
Account(-5000)     →  ValueError: balance cannot be negative   __init__ validated too

    That last line is the part the getter version cannot do. Assigning in __init__ runs the setter, so the object cannot be born invalid — the whole point of encapsulation, and it arrived without a single get_ method.

    Notes
    If you genuinely want read-only
    class Account:
    def __init__(self, balance): self._balance = balance

    @property
    def balance(self): return self._balance    getter only, no setter

a.balance      →  5000
a.balance = 1  →  AttributeError: property 'balance' of 'Account' object has no setter

    A property with no setter is enforced. __balance with no set_balance is not — as the -999 above showed.

    When a get_ method IS right
    account.balance              cheap attribute read
account.get_statement()      hits the database — looks expensive, is expensive
account.calculate_interest() computes; the name says so

    Attribute syntax sets an expectation of “this is cheap”. If the work is slow, does I/O, or can fail, a method is the honest signature. A property hiding a network call is a trap for the next reader.

    In an interview

    “Python does not use getters and setters; it uses @property, because attribute access and method access are interchangeable to the caller.” Then the follow-up worth having ready: and __ is name mangling, not access control — see snippet 18.
