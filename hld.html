Foundations — 4 topics

Networking is the other foundation of system design — DNS, TCP, HTTP, TLS. It outgrew this section and now has its own track: Networking →

  1. Capacity estimation

    Back-of-envelope maths that justifies every later decision: QPS from daily actives, storage from write volume × retention, bandwidth from payload size. Do this first in an interview — it's what turns "add a cache" from a guess into a conclusion.

    Resources
    Learn
    • Latency numbers every programmer should know — memorise these
    • System Design Primer — powers of two & estimation
    • Hello Interview — System Design in a Hurry — shows where estimation fits in the 45 minutes

    No LeetCode — estimate QPS and storage for your own crawler and marketplace, then check against reality.

  2. Scaling & statelessness

    Vertical scaling hits a ceiling; horizontal scaling needs services that hold no local state. Push sessions into Redis or a signed token so any instance can serve any request, then scale web, worker and database tiers independently.

    Resources
    Learn
    • The Twelve-Factor App — factor VI (processes) is exactly this
    • System Design Primer — application layer
    • Django sessions — where the state actually lives
    Practice

    No LeetCode — run two instances of one of your apps behind a proxy and find what breaks.

    My code

  3. Load balancing

    Spreading traffic across instances: L4 (TCP) versus L7 (HTTP, can route on path or header), the algorithms — round robin, least connections, consistent hashing for stickiness — plus health checks and connection draining so a dying instance stops receiving traffic.

    Resources
    Learn

  4. Reverse proxy & API gateway

    The single front door: TLS termination, routing, auth, rate limiting and request shaping before traffic ever reaches your application. A reverse proxy handles transport concerns; a gateway adds cross-cutting application concerns.

Data & Storage — 8 topics

  1. SQL vs NoSQL & data modelling

    Choosing a store from the access pattern, not from fashion. SQL when you need relationships and transactions; NoSQL when the query shape is known and scale matters more than flexibility. Normalise for correctness, then denormalise deliberately for read speed.

    Resources
    Learn
    • Designing Data-Intensive Applications — chapter 2 is the definitive treatment
    • System Design Primer — database
    • PostgreSQL data types — knowing these well is underrated
    Practice

  2. Indexing & query optimisation

    Why a query is slow and what to do about it: B-tree vs hash indexes, leftmost-prefix rules for composite indexes, covering indexes that avoid the table lookup, and the fact that every index you add slows writes down.

    Resources

  3. Caching

    The biggest single lever on read-heavy systems, and the biggest source of stale-data bugs. Cache-aside vs write-through vs write-back, LRU/LFU/TTL eviction, and the three failure modes: stampede, penetration and avalanche.

  4. CDN & object storage

    Large and static content never belongs on your app servers. Object storage holds the bytes, a CDN caches them near the user, and pre-signed URLs give a specific user time-limited access without the request ever touching your backend.

  5. Replication

    Copies of your data on more than one machine, for read scale and for survival. Leader–follower topology, sync vs async trade-offs, replication lag and the "user can't see their own write" bug, plus failover and why you need a quorum. Replicas scale reads, never writes.

  6. Partitioning & sharding

    Splitting data across machines once one box can't hold the writes. Range partitioning gives cheap scans but risks hotspots; hash partitioning spreads evenly but loses range queries. The shard key is the one decision you can't cheaply undo.

  7. Search & ranking

    Turning documents into something queryable: inverted indexes, tokenisation and analysers, relevance scoring, and — increasingly — hybrid retrieval that combines keyword matching with vector similarity, then re-ranks the merged result.

  8. Geospatial indexing

    Answering "what's near me" without scanning every row. Geohash turns coordinates into sortable string prefixes; QuadTrees subdivide space adaptively; H3 uses hexagons to keep neighbour distances uniform. The basis of every ride-sharing and delivery design.

Distributed Systems — 9 topics

  1. Consistency models & CAP

    CAP says that during a network partition you choose consistency or availability — it says nothing about normal operation, which is where most people misuse it. The useful vocabulary is the middle ground: read-your-writes, monotonic reads, and quorum reads/writes.

    Resources
    Learn
    • Jepsen — consistency models map — the reference hierarchy
    • Kleppmann — Please stop calling databases CP or AP
    • Kleppmann — Distributed Systems lectures — free, full university course
    Practice

  2. Transactions & isolation levels

    ACID in practice: which anomalies each isolation level permits — dirty reads, non-repeatable reads, phantoms — and what that costs in lock contention. Postgres uses MVCC, so readers don't block writers, which changes the trade-offs from what textbooks assume.

    Resources
    Learn

  3. Distributed transactions

    Keeping several services consistent without a single database transaction. Two-phase commit blocks on a coordinator failure; sagas break the work into steps with compensating actions; the transactional outbox makes "write to DB and publish an event" atomic.

  5. Event-driven architecture

    Services that react to events instead of calling each other directly. An append-only log like Kafka keeps history so new consumers can replay it; ordering is guaranteed per partition, never globally, which shapes how you choose a partition key.

  7. Idempotency & deduplication

    Since almost every distributed system delivers at-least-once, the same message will arrive twice — so handlers must be safe to replay. Idempotency keys, deduplication tables and conditional updates are how you get exactly-once behaviour without exactly-once delivery.

  8. Consistent hashing

    Plain hash % N remaps almost every key when N changes, which empties a cache cluster on a single node addition. Consistent hashing places nodes on a ring so only ~1/N of keys move, and virtual nodes even out the distribution.

    When several instances must agree who is in charge: distributed locks, consensus protocols like Raft and Paxos, and the systems that implement them (etcd, ZooKeeper). Split-brain — two nodes both believing they lead — is the failure this prevents.

Reliability & Operations — 7 topics

  1. Rate limiting & throttling

    Protecting a service from being overwhelmed, and being a good client of someone else's. Token bucket allows bursts and is the usual answer; fixed windows leak a 2× burst at the boundary, which sliding windows fix. Distributed limiting needs shared atomic counters.

    Resources
    Learn
    • Cloudflare — sliding window rate limiting
    • Redis — rate limiting patterns
    • Stripe — Scaling your API with rate limiters
    Practice
    • Logger Rate Limiter
    • Design Hit Counter
    My code
    • Rate-limiter — fixed-window limiter; sliding window is the next step

  2. Probabilistic data structures

    Trading exactness for enormous memory savings. A Bloom filter answers "definitely not present" or "probably present" with no false negatives; count-min sketch approximates frequencies; HyperLogLog counts uniques in kilobytes instead of gigabytes.

    Resources
    Learn
    • Interactive Bloom filter tutorial
    • Redis probabilistic data types
    • DDIA — where these appear in real storage engines
