LLD Concepts

Low-level design — how classes and objects are structured. This is the track that decides whether a codebase stays changeable. Open Resources on any topic for the material I learn from, problems to practise on, and my own code.

  1. SOLID principles

    Five rules that keep classes small and swappable: single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion. Dependency inversion is the one that pays off most — depend on an abstraction, inject the concrete thing.

    Resources
    Learn
    • Uncle Bob — SOLID Relevance — from the person who named them
    • DigitalOcean — SOLID explained — short, with examples
    • awesome-low-level-design — SOLID section with code
    Practice

    No direct LeetCode equivalent — practise by refactoring one of your own classes until each has a single reason to change.

    My code
    • lenny-growth-assistant — the LiteLLM router is dependency inversion in practice: the agent depends on "an LLM", not on OpenAI

  2. Design principles & code smells

    DRY, KISS, YAGNI and the Law of Demeter — plus the ability to name what's wrong with a piece of code. God classes, long methods, feature envy, shotgun surgery and primitive obsession are the smells worth recognising on sight.

    Resources
    Learn
    • Refactoring Guru — Code Smells — each smell with its refactoring
    • Martin Fowler — Code Smell — the original framing
    • Refactoring Guru — Techniques — the fixes, step by step
    Practice

    Not a LeetCode skill — pick an old file of yours and refactor it against this list.

    Nothing yet — a good candidate is a before/after refactor repo.

  3. UML — class & sequence diagrams

    The shared vocabulary for sketching a design before coding it: association, aggregation, composition and inheritance between classes, and sequence diagrams for the flow through them. In an interview this is how you show the design without writing code.

    Resources
    Learn
    • UML class diagram tutorial — relationships and notation
    • Mermaid class diagrams — draw them as text, keep them in the repo
    • Excalidraw — what to actually use in an interview
    Practice

    Draw the class diagram for a system you've already built before looking at the code.

  4. Creational patterns

    Patterns that control how objects get made, so construction logic doesn't leak across the codebase: Factory, Abstract Factory, Builder, Singleton, Prototype. The interview cue is "how do you add a new provider without touching existing code?"

  5. Structural patterns

    How objects compose into bigger structures: Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight. Worth knowing the distinction — a decorator adds capability, a proxy controls access, an adapter changes the interface.

  6. Behavioural patterns

    How objects communicate and share responsibility: Strategy, Observer, State, Command, Template Method, Chain of Responsibility, Iterator, Mediator. You've already used two of these — Django middleware is Chain of Responsibility, Django signals are Observer.

  7. Layering & clean architecture

    Separating domain logic from the application layer and from infrastructure, so the framework sits at the edge rather than through the middle. In Django terms: business rules out of views and models, into a service layer that can be tested without a request.

    Resources
    Learn
    • Architecture Patterns with Python — free online, Django/service-layer focused
    • Uncle Bob — The Clean Architecture — the original post
    • HackSoft Django Styleguide — the service-layer pattern, applied
    Practice

    Take an existing fat view and pull the logic into a service you can call from a test.

    My code

  8. Error handling & API contracts

    Designing what a method promises and what it does when it can't keep that promise: exception hierarchies, fail-fast vs recover, validating at the boundary, and never letting an infrastructure exception leak into domain code.

    Resources
    Learn
    • Python — Errors and Exceptions
    • DRF exception handling — mapping domain errors to HTTP
    • Google Python Style Guide — the exceptions section is opinionated and good
    Practice

    Design an exception hierarchy for one of your projects, then make every API error map to exactly one class.

    My code
    • logging — loggers and handlers, the other half of failure handling

  9. Testability & mocking

    Writing classes that can be tested without a database, a network or a clock. The design skill is creating seams — inject dependencies rather than constructing them inside, so a fake can take their place.

    Resources
    Learn
    • pytest docs — fixtures are the dependency-injection mechanism
    • unittest.mock — patch, MagicMock, autospec
    • Fowler — Mocks Aren't Stubs — the distinction that matters
    Practice

    Add tests to an existing repo without touching a real database — whatever you have to change to do that is the lesson.
