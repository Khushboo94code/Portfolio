SDLC phases

Every methodology does these; they differ in the order and the size of the loop.

PhaseWhat happensOutput
RequirementsGather what is needed and whyRequirement docs, user stories
DesignArchitecture and interfaces — HLD then LLDDesign docs, ER and class diagrams
ImplementationWrite the codeWorking software in version control
TestingUnit, integration, system, acceptanceTest reports, defect list
DeploymentRelease to usersRunning system
MaintenanceFix, improve, adaptPatches and new versions

Methodologies

ModelHow it worksBest forWeakness
WaterfallPhases in strict sequenceFixed, well-understood requirementsNo feedback until the end
AgileShort iterations, continuous feedbackChanging requirements — most productsNeeds discipline and real customer access
ScrumAgile with fixed-length sprints and rolesTeams delivering features regularlyCeremony overhead if applied blindly
KanbanContinuous flow, limit work in progressSupport and ops workNo fixed cadence to plan around
SpiralIterations driven by risk analysisLarge, high-risk systemsHeavyweight
V-modelEach build phase paired with a test phaseSafety-critical workAs rigid as waterfall

Scrum — roles, events, artifacts

Read the Scrum Guide once; it is 13 pages and settles most arguments.

ItemTypeWhat it is
Product OwnerRoleOwns the backlog and its priority — the "what"
Scrum MasterRoleRemoves blockers, protects the process — not a manager
DevelopersRoleThe people building it — the "how"
SprintEventA fixed-length iteration, usually 1-4 weeks
Sprint PlanningEventChoose what the sprint will deliver
Daily StandupEvent15 minutes: progress, plan, blockers
Sprint ReviewEventDemo the increment to stakeholders
RetrospectiveEventImprove the process, not the product
Product BacklogArtifactEverything wanted, ordered by value
Sprint BacklogArtifactWhat this sprint committed to
IncrementArtifactThe shippable result of the sprint

Agile vocabulary

TermMeaning
User story"As a <role>, I want <goal>, so that <benefit>"
Acceptance criteriaThe conditions that make a story done
Definition of DoneThe team-wide bar — tested, reviewed, documented, deployed
Story pointsRelative effort, not hours — often Fibonacci
VelocityPoints completed per sprint; used to forecast, never to compare teams
EpicA large body of work split into stories
SpikeA timeboxed investigation to reduce uncertainty
Burndown chartWork remaining against time in the sprint
Backlog groomingRefining and re-ordering upcoming work
Technical debtShortcuts taken now that cost interest later
WIP limitCap on in-progress items — the core Kanban idea
MVPSmallest version that delivers and validates value

Engineering practices around the cycle

These are what actually make short iterations safe — agile without them is just shipping faster with more bugs.

PracticeWhy it exists
Version controlEvery change traceable and revertible — see the Git track
Code reviewCatches defects and spreads knowledge; small PRs get reviewed properly
Continuous integrationMerge and test often so integration is never a phase
Continuous deliveryEvery commit is releasable — see the Deployment track
Automated testingThe only thing that makes frequent change safe
RefactoringImprove structure without changing behaviour — continuously, not as a project
Pair programmingReal-time review; good for hard problems and onboarding
Blameless postmortemsLearn from incidents without making people hide them

Testing levels

LevelScopeWho usually writes it
UnitOne function or class in isolationThe developer
IntegrationSeveral components together, real databaseThe developer
System / E2EThe whole application through its interfaceQA or the developer
Acceptance (UAT)Does it meet the requirementProduct or the customer
RegressionDid a change break something that workedAutomated in CI
SmokeIs the build fundamentally aliveAutomated after deploy
