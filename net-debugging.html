Debugging & Performance — 4 topics

The part that actually gets used on the job — and the part most candidates can't demonstrate.

  1. Latency, throughput & RTT

    Bandwidth is how much fits in the pipe; latency is how long one trip takes — and you can buy more bandwidth but not less distance. Since every round trip costs RTT, reducing the number of round trips beats making each one faster.

    Resources
    Learn
    • HPBN — primer on latency and bandwidth

    • Network delay — Wikipedia
    Practice
    • Measure RTT to servers on three continents and relate the numbers to physical distance.
    • Count the round trips in one cold page load: DNS, TCP, TLS, then the request itself.

  2. Tooling — dig, curl, traceroute, tcpdump

    The diagnostic kit: dig for DNS, curl -v for the full HTTP exchange, traceroute for the path, ss for socket states, and tcpdump or Wireshark when you need the packets themselves. Being fluent here is a visible differentiator.

    Resources
    Learn
    • Wireshark User's Guide
    • curl manual — far more than -v
    • Julia Evans' zines — networking debugging made genuinely approachable
    Practice
    • Capture a full page load in Wireshark and find the DNS lookup, TCP handshake and TLS handshake.
    • Debug a failing request using only curl -v and dig.

  3. Common failure modes

    The recurring ones: timeouts versus connection refused versus DNS failure — three different causes people report identically; stale DNS after a cutover; MTU mismatch causing large requests to hang; and connection pool exhaustion under load.

    Resources
    Learn
    • AWS — timeouts, retries and backoff with jitter
    • Google SRE — addressing cascading failures
    • Julia Evans — debugging guides
    Practice
    • Explain the difference between a connection timeout and a read timeout, and set both correctly in one HTTP client.
    • Find every external call in your code with no timeout set.

    • lenny-growth-assistant — provider fallback when an upstream call fails

  4. Connection reuse & tuning

    Since a new HTTPS connection costs DNS plus TCP plus TLS round trips, reusing connections is usually the largest available win: keep-alive, HTTP client session objects, and database connection pooling. Compression and payload size come after that.

    Resources

    • PgBouncer — pooling at the database edge
    Practice
    • Benchmark 100 requests with a fresh connection each time versus one reused session.
    • Find any code making repeated HTTP calls without a session and fix it.
