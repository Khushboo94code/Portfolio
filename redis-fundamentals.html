Fundamentals — 5 topics

  1. What Redis is

    An in-memory data structure server — not just a cache. It holds strings, hashes, lists, sets and sorted sets in RAM and serves them in microseconds, which is why the same process can be your cache, your queue broker, your rate limiter and your session store.

  2. The single-threaded model

    Command execution is single-threaded, which sounds like a limitation and is actually the source of its guarantees — every command is atomic because nothing runs beside it. The consequence: one slow command (KEYS * on a big database) blocks every other client.

  3. Keys, TTL & expiry

    Everything is a key, and any key can have a time to live. Expiry is how a cache stays a cache rather than growing forever — and Redis expires lazily plus in background sampling, so a key is not necessarily removed the instant it expires.

  4. Persistence — RDB & AOF

    Redis can snapshot to disk (RDB) or append every write to a log (AOF), or both. RDB is compact and loses the window since the last snapshot; AOF loses almost nothing and replays slower on restart. A cache may need neither — a queue certainly does.

  5. Transactions & Lua scripts

    MULTI/EXEC queues commands and runs them without interleaving; WATCH adds optimistic locking. Lua scripts run atomically on the server, which is how you do read-modify-write in one round trip — the correct way to build a rate limiter.
